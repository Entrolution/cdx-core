# Extension Development Guide

This guide covers how extensions work in cdx-core: the built-in extension types, how to register extensions in the manifest, namespace conventions, archive storage, and how the macro system generates document accessors.

## Extension Architecture

Extensions add domain-specific functionality to Codex documents without modifying the core content model. Each extension:

- Lives in its own namespace (e.g., `forms`, `semantic`, `collaboration`)
- Stores data in a dedicated archive path (e.g., `forms/data.json`)
- Is declared in the manifest with an ID, version, and required flag
- Gets document-level accessors generated by the `define_extension_accessors!` macro

## Built-in Extensions

| Namespace | Archive Path | Data Type | Purpose |
|-----------|-------------|-----------|---------|
| `academic` | `academic/numbering.json` | `NumberingConfig` | Theorem/equation numbering |
| `collaboration` | `collaboration/comments.json` | `CommentThread` | Comments, change tracking, sessions |
| `forms` | `forms/data.json` | `FormData` | Interactive form fields |
| `phantom` | `phantoms/clusters.json` | `PhantomClusters` | Off-page annotation clusters |
| `semantic` | `semantic/bibliography.json` | `Bibliography` | Citations, glossary, entity linking |
| (metadata) | `metadata/jsonld.json` | `JsonLdMetadata` | JSON-LD structured metadata |

## Namespace Conventions

Namespaces are defined as constants in `extensions::namespaces`:

```rust
pub mod namespaces {
    pub const FORMS: &str = "forms";
    pub const SEMANTIC: &str = "semantic";
    pub const COLLABORATION: &str = "collaboration";
    pub const ACADEMIC: &str = "academic";
    pub const LEGAL: &str = "legal";
    pub const PRESENTATION: &str = "presentation";
}
```

### Block Type Format

Extension blocks use `"namespace:blockType"` notation:

```
forms:textInput
semantic:citation
collaboration:comment
academic:theorem
legal:cite
```

An `ExtensionBlock` stores the namespace and block type separately:

```rust
let block = Block::extension("forms", "textInput");
```

Parsing helpers:

```rust
ExtensionBlock::parse_type("forms:textInput")  // Some(("forms", "textInput"))
ext.full_type()                                  // "forms:textInput"
ext.is_namespace("forms")                        // true
ext.is_type("forms", "textInput")                // true
```

### Extension Marks

Inline extension marks on text spans use the same namespace convention via `ExtensionMark`:

```rust
ExtensionMark::citation("ref-smith2024")                    // emits {"refs": ["ref-smith2024"]}
ExtensionMark::citation_with_page("ref-smith2024", "42")    // emits {"refs": ["ref-smith2024"], "locator": "42", ...}
ExtensionMark::multi_citation(&["smith2023".into(), "jones2024".into()])
ExtensionMark::entity("https://www.wikidata.org/wiki/Q42", EntityType::Person)
ExtensionMark::glossary("term-algorithm")
ExtensionMark::index("Machine learning")
ExtensionMark::index_subterm("Algorithms", "Sorting")
```

## Manifest Registration

Extensions must be declared in the manifest to be recognized:

```rust
use cdx_core::manifest::Extension;

// Required extension - readers that don't support it must reject the document
let ext = Extension::required("codex.semantic", "0.1");

// Optional extension - readers can safely ignore it
let ext = Extension::optional("codex.forms", "0.1");
```

The ID format is `"codex.{namespace}"` for built-in extensions. Custom extensions use `"org.example.custom"`.

Query extensions on a manifest:

```rust
manifest.has_extension("semantic")        // true/false
manifest.get_extension("semantic")        // Option<&Extension>
manifest.declared_extension_ids()         // Vec<&str>
```

### Required vs Optional

- **Required** (`required: true`): A reader that does not support this extension must reject the document. Use this when the extension content is essential to understanding the document.
- **Optional** (`required: false`): A reader can ignore the extension and still render the document meaningfully. Use this for supplementary features.

## Fallback Content

Extension blocks can include fallback content for renderers that don't support the extension:

```rust
let form_block = ExtensionBlock::new("forms", "textInput")
    .with_fallback(Block::paragraph(vec![Text::plain("[Form field: Full Name]")]));
```

This renders as a plain paragraph in readers that don't understand forms. In JSON:

```json
{
  "type": "forms:textInput",
  "id": "name-field",
  "label": "Full Name",
  "required": true,
  "fallback": {
    "type": "paragraph",
    "children": [{"value": "[Form field: Full Name]"}]
  }
}
```

Fallback is optional but recommended for any extension marked as optional.

## Document Accessors

The `define_extension_accessors!` macro generates five methods per extension field on `Document`:

```rust
// For the `comments` field with type `CommentThread`:
doc.comments()            // -> Option<&CommentThread>
doc.comments_mut()        // -> Result<Option<&mut CommentThread>>
doc.has_comments()        // -> bool
doc.set_comments(thread)  // -> Result<()>
doc.clear_comments()      // -> Result<()>
```

The mutable methods (`_mut`, `set_`, `clear_`) check document state and return `Error::ImmutableDocument` if the document is frozen or published.

### Available Accessor Sets

| Field | Type | Getter | Has | Set | Clear |
|-------|------|--------|-----|-----|-------|
| `academic_numbering` | `NumberingConfig` | `academic_numbering()` | `has_academic_numbering()` | `set_academic_numbering()` | `clear_academic_numbering()` |
| `comments` | `CommentThread` | `comments()` | `has_comments()` | `set_comments()` | `clear_comments()` |
| `phantom_clusters` | `PhantomClusters` | `phantom_clusters()` | `has_phantom_clusters()` | `set_phantom_clusters()` | `clear_phantom_clusters()` |
| `form_data` | `FormData` | `form_data()` | `has_form_data()` | `set_form_data()` | `clear_form_data()` |
| `bibliography` | `Bibliography` | `bibliography()` | `has_bibliography()` | `set_bibliography()` | `clear_bibliography()` |
| `jsonld_metadata` | `JsonLdMetadata` | `jsonld_metadata()` | `has_jsonld_metadata()` | `set_jsonld_metadata()` | `clear_jsonld_metadata()` |

## Archive Storage

Extension data is stored as JSON files at well-known paths inside the `.cdx` archive:

```
archive.cdx (ZIP)
├── manifest.json
├── content/
│   └── document.json
├── metadata/
│   ├── dublin-core.json
│   └── jsonld.json           (optional, JSON-LD)
├── academic/
│   └── numbering.json        (optional)
├── collaboration/
│   └── comments.json         (optional)
├── phantoms/
│   └── clusters.json         (optional)
├── forms/
│   └── data.json             (optional)
├── semantic/
│   └── bibliography.json     (optional)
└── security/
    ├── signatures.json        (optional)
    └── encryption.json        (optional)
```

Extension files are written with Deflate compression. The reading and writing patterns are:

```rust
// Reading (in Document::from_reader)
let comments = reader.read_optional_json::<CommentThread>(COMMENTS_PATH)?;

// Writing (in Document::write_to)
if let Some(ref comments) = self.comments {
    let json = serde_json::to_vec_pretty(comments)?;
    writer.write_file(COMMENTS_PATH, &json, CompressionMethod::Deflate)?;
}
```

## Extension-Specific Details

### Forms

Form fields are represented as extension blocks in the content tree. The `FormField` enum provides typed access:

```rust
use cdx_core::extensions::FormField;

// Parse an extension block into a typed form field
if let Some(field) = FormField::from_extension(&ext_block) {
    println!("Label: {}", field.label());
    println!("Required: {}", field.is_required());
}
```

Field types: `TextInput`, `TextArea`, `Checkbox`, `RadioGroup`, `Dropdown`, `DatePicker`, `Signature`.

Form responses are stored in `FormData` (a map of field ID to value).

### Semantic

The semantic extension spans multiple subsystems:

- **Bibliography** (`Bibliography`, `BibliographyEntry`): Reference management with support for APA, Chicago, Harvard, IEEE, MLA, Vancouver citation styles.
- **Citations** (`Citation`): Inline citation marks with locator support (page, chapter, section).
- **Glossary** (`Glossary`, `GlossaryTerm`): Term definitions with aliases and cross-references.
- **Entity Linking** (`EntityLink`): Links to knowledge bases (Wikidata, DBpedia, VIAF) with entity types (Person, Place, Organization, Event, Work, Concept).
- **JSON-LD** (`JsonLdMetadata`): Structured metadata for semantic web integration.

### Collaboration

The collaboration extension covers real-time and async workflows:

- **Comments** (`CommentThread`, `Comment`): Threaded comments with types (comment, highlight, suggestion), priority levels, and resolution tracking.
- **Change Tracking** (`ChangeTracking`, `TrackedChange`): Insertions, deletions, replacements, and formatting changes with accept/reject workflow.
- **Sessions** (`CollaborationSession`): Real-time collaboration with participant cursors and selections.
- **CRDT** (`CrdtMetadata`): Conflict-free replicated data type metadata for peer synchronization.
- **Revision History** (`RevisionHistory`, `Revision`): Version history with materialization events.

### Academic

Structured content types for academic writing:

- **Theorems** (`Theorem`): With variants Theorem, Lemma, Proposition, Corollary, Conjecture, Axiom, Definition.
- **Proofs** (`Proof`): With methods Direct, Contradiction, Induction, Construction.
- **Exercises** (`Exercise`, `ExerciseSet`): With difficulty levels and optional hints/solutions.
- **Algorithms** (`Algorithm`): Pseudocode with parameters.
- **Abstracts** (`Abstract`): Structured abstracts with sections (Background, Objectives, Methods, Results, Conclusions).
- **Numbering** (`NumberingConfig`): Configurable numbering with style patterns (`number`, `chapter.number`, `section.number`, `chapter.section.number`) and heading-level reset triggers.

### Legal

Legal document support:

- **Citations** (`LegalCitation`): With categories Case, Statute, Regulation, Rule, Constitution. Supports Bluebook, ALWD, and Chicago citation formats.
- **Table of Authorities** (`TableOfAuthorities`): Auto-generated citation tables by category.
- **Court Captions** (`Caption`): Structured case headers with parties and counsel.
- **Signature Blocks** (`SignatureBlock`): Legal signature capture with date and location.

### Phantom Clusters

Off-page annotations attached to content anchors:

```rust
use cdx_core::extensions::{PhantomClusters, PhantomCluster, PhantomScope};

let cluster = PhantomCluster::new("cluster-1", "block-anchor-id")
    .with_scope(PhantomScope::Shared);

let mut clusters = PhantomClusters::new();
clusters.add_cluster(cluster);
```

Phantom clusters support scoping (`Shared`, `Private`, `RoleRestricted`), spatial positioning, and connections between phantoms.

## Validation

`Document::validate_extensions()` checks consistency between declared extensions in the manifest and extensions actually used in content blocks and marks. This helps catch:

- Extensions used in content but not declared in the manifest
- Extensions declared in the manifest but not used
- Namespace mismatches
